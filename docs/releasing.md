# Releasing

Orglane is released from `main` with [release-please](https://github.com/googleapis/release-please). Versions follow [Semantic Versioning](https://semver.org) and are computed from the Conventional Commits on `main`. **A release is a human decision** ([ADR 0017](adr/0017-development-process.md)): automation prepares it, a maintainer cuts it.

## How a release happens

1. The **Release** workflow (`.github/workflows/release.yml`) keeps one release pull request open, titled `chore: release X.Y.Z`. It bumps `.release-please-manifest.json` and adds the `CHANGELOG.md` entry. The workflow runs once a day and on demand:

   ```sh
   gh workflow run release.yml   # refresh the release pull request now
   ```

2. A maintainer reviews the pull request (the version and the changelog) and squash-merges it. Both files are `risk/high`, so the merge gate never merges it on its own. CI does not run on it: it is created with `GITHUB_TOKEN`, whose events start no workflows, and it changes only the changelog and the manifest.
3. The merge changes the manifest, so the Release workflow runs again. release-please tags the merge commit `vX.Y.Z` and publishes the GitHub release with the changelog entry.
4. In the same run, the **Images** workflow (`.github/workflows/images.yml`) builds and publishes the container images.

Before 1.0, `feat` and breaking changes bump the minor version and everything else the patch version. The first release is `0.1.0`. Only `feat`, `fix`, `perf` and `revert` commits appear in the changelog. To force a version, add `Release-As: X.Y.Z` to the body of a commit on `main`.

## Container images

Images are published to `ghcr.io/orglane/orglane` for `linux/amd64` and `linux/arm64`:

| Release tag | Image tags |
|---|---|
| `v0.2.0` (newest release) | `0.2.0`, `0.2`, `latest` |
| `v0.1.5` (after `v0.2.0`) | `0.1.5`, `0.1` |
| `v0.3.0-rc.1` (prerelease) | `0.3.0-rc.1` |

`latest` and the minor tags only move forward, even when release runs overlap. The Images workflow has two jobs:

- **build** runs for each release in parallel. It pushes the image by digest, verifies it, and only then tags the exact version. Exact tags belong to one release, so parallel builds cannot clash.
- **promote** moves `latest` and the `X.Y` tags. It runs in a single concurrency group (`images-promote`) for all releases. Right before moving anything, it lists the tags in the registry and recomputes every alias from them (`go run ./tools/ci release-aliases`; the workflow token is sent only to the registry's own origin, and redirects are refused): `latest` goes to the newest published release, each `X.Y` to the newest published patch of its line. A release that finishes after a newer one (v0.1.0 after v0.1.1) therefore leaves the aliases alone. GitHub cancels an older *pending* promotion when another one queues; that is harmless, because the run that does start reconciles every alias. Prereleases are never promoted.

`tools/ci/internal/release` tests this against every order of builds and promotions of overlapping releases, including canceled promotions.

There is no `edge` image of `main` yet, because building one on every merge would cost too many Actions minutes while the repository is private.

Each image:

- is built from the root `Dockerfile` (distroless, non-root). The binary reports the release version: `docker run --rm ghcr.io/orglane/orglane:0.1.0 cli version` prints `orglane 0.1.0`;
- carries an SPDX **SBOM** and a SLSA **provenance** attestation, generated by BuildKit:

  ```sh
  docker buildx imagetools inspect ghcr.io/orglane/orglane:0.1.0 --format '{{json .SBOM}}'
  docker buildx imagetools inspect ghcr.io/orglane/orglane:0.1.0 --format '{{json .Provenance}}'
  ```

- takes about 4 minutes to build and publish (both platforms, cold cache);
- is checked before any tag points at it (`.github/scripts/verify-image.sh`): both platforms, both attestations, and `cli version` on each platform;
- is **signed with cosign** (keyless, GitHub OIDC) once the repository is public. Keyless signatures are recorded in Sigstore's public transparency log, which would disclose the private repository's name and workflow, so the signing step is skipped while the repository is private. Once it is public, verify with:

  ```sh
  cosign verify ghcr.io/orglane/orglane:0.1.0 \
    --certificate-identity-regexp '^https://github.com/orglane/orglane/\.github/workflows/images\.yml@refs/' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
  ```

## Prereleases

Prereleases are tagged by hand and publish only their exact image tag. No GitHub release is created.

```sh
git tag v0.2.0-rc.1 <commit on main>
git push origin v0.2.0-rc.1
```

To remove a test prerelease, delete the tag and its package versions. A multi-arch push creates one tagged version (the index) and four untagged ones (two platform images, two attestations); delete those too:

```sh
git push origin :refs/tags/v0.2.0-rc.1
gh api orgs/orglane/packages/container/orglane/versions \
  --jq '.[] | "\(.id) \(.name) \(.metadata.container.tags)"'
gh api -X DELETE orgs/orglane/packages/container/orglane/versions/<id>
```

## One-time repository setup

- **Settings → Actions → General → Workflow permissions:** enable *Allow GitHub Actions to create and approve pull requests*. release-please cannot open the release pull request with `GITHUB_TOKEN` otherwise.
- The first push creates the `orglane` container package, linked to the repository and private like it. Make it public when the repository goes public.
